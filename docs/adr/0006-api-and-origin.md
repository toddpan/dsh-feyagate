# ADR-0006：同源 HTTP 管理 API + Origin 校验，默认只绑 loopback

> **这个文件解决什么问题**：回答"插件给浏览器的接口怎么防滥用"，以及"子进程该绑哪个地址"。

- **Status**：Accepted
- **Date**：2026-09-25
- **相关**：[ADR-0002](0002-install-directory.md)、[ADR-0007](0007-open-source-boundary.md)、[`src/constants.ts`](../../src/constants.ts)

---

## Context

插件有一个"浏览器半侧必须调 Host 半侧"的需求：设置面板要读服务状态、发起安装/升级、读日志、写授权码。这些动作的威力不小 —— 安装会在本机写文件并启动进程、卸载会删目录、升级会替换二进制。

DSH 侧的既有事实：

- 插件 Host 代码**没有权限机制**，以宿主用户完整权限在进程内运行；沙箱只约束模型可见的 bash/fs，不约束插件。
- 浏览器半侧只能发**同源** HTTP 请求；它需要知道 API 前缀。DSH 的设置页可能在**远程部署**下被非本机浏览器打开，此时"管理本机后台服务"这个动作在语义上根本不成立。
- 前端 baseline 只白名单 9 个模块，插件需要的前端包必须显式声明；这与"页面怎么拿到 API 前缀"无关，但同属"浏览器半侧的边界"。

子进程侧的事实：上游模板 `config.yaml.example` 的默认是 `server.bind_address: "0.0.0.0"`，也就是**默认对局域网开放**，而且 MCP HTTP 端点（`POST /mcp/http`）在本机上不校验任何身份。这是必须由界面承担的告知义务，不能只在文档里写一句。

## Decision

### 1. 管理 API：同源、带前缀、校验 Origin

- 前缀 `/dsh-feyagate/*`（[`src/constants.ts`](../../src/constants.ts) 的 `API_PREFIX`），全部响应走统一信封 `ApiEnvelope<T> = { ok: true; data } | { ok: false, error }`（[`src/types.ts`](../../src/types.ts)）。
- 浏览器半侧不硬编码前缀：Host 通过注入全局 `__DSH_FEYAGATE__`（`BROWSER_GLOBAL`）告诉它，因为这个前缀是插件设置项。
- **写操作校验 Origin**（[`src/api.ts`](../../src/api.ts) 的 `checkOrigin`）：把请求 `Origin` 头的 host 与请求 `Host` 头比对，不一致直接 `403`。**非浏览器客户端（curl、脚本）不带 `Origin`，被放行** —— 浏览器在跨站写请求上**无法**省略 `Origin`，所以这条足以关掉 CSRF 路径，又不会把命令行工具挡在门外。不依赖 `Sec-Fetch-Site` 等只有新浏览器才有的头。
- **非 loopback 访问降级为只读**：页面不是从运行 DSH 的那台机器打开时，所有写操作按钮禁用并说明原因（错误码 `FG-API-403`，文案："后台服务只能在运行 DSH 的那台电脑上管理"）。这既是安全策略也是事实 —— 远程浏览器确实管不了那台机器上的进程。
- **只读部署**：DSH 把设置标为只读时，整卡显示"本部署的设置为只读。"并禁用字段（复用 DSH 既有文案）。

### 2. 网络绑定：默认只绑 loopback

| 组件 | 默认绑定 | 说明 |
|---|---|---|
| 管理 API（Host） | 由 DSH 宿主的监听地址决定，随宿主 | 插件不额外开监听 |
| MCP 门面 | `127.0.0.1:38081` | **不支持**改成 `0.0.0.0`；它只服务本机的桥 |
| 子进程 HTTP | `127.0.0.1:38080`（生成物里写 `bind_address: 127.0.0.1`） | **与上游模板的 `0.0.0.0` 不同，这是有意的收紧** |

要开局域网（手机/音箱直连）必须**用户显式开启**，开启时界面同时给出警告（UX 文档 §3.4 的原文）：

> ⚠ 局域网内其他设备可以访问你的后台服务，且本地接口不校验身份。仅在需要手机或音箱直连时开启，并确保你的 Wi-Fi 可信。

**为什么这条警告是硬性要求**：上游默认 `0.0.0.0`，而 MCP HTTP 端点无鉴权。用户把默认值留在那里就等于把设备控制接口暴露在局域网里 —— 这件事必须由界面说，不能只写在文档。

### 3. 不做的事

- **不做自建鉴权体系**（不发 token、不做登录页）：插件的威胁模型是"本机浏览器 + 同源页面"，加一层自研 token 只会增加状态而挡不住本地进程。
- **不把管理 API 开成公网可访问**。
- **不在子进程与宿主之间加 TLS**：两者都在本机 loopback，加 TLS 只是仪式（还要处理自签证书的信任问题）。

## Consequences

**得到：**

- 恶意的跨站页面无法通过浏览器驱动这台机器安装/卸载二进制（Origin 校验 + 同源 Fetch Metadata）。
- 远程打开设置面板时，界面**如实**说"你管不了这台机器"，而不是给一堆点了没反应的按钮（"不允许点了没反应"是 UX 硬规则）。
- 局域网暴露从"默认开启"变成"默认关闭 + 显式开启 + 当时就警告"。

**付出：**

- 需要处理"宿主 origin 未知"的边缘情形（例如 DSH 监听 `0.0.0.0` 而页面从 `127.0.0.1` 打开，origin 是 `http://127.0.0.1:<port>`）。策略：以宿主实际 origin 集合为准，匹配不上则只允许读操作。
- 用户若真的需要手机直连，必须去端口页手动改绑定地址（比上游"开箱即 0.0.0.0"麻烦，这是有意的）。
- 只读降级会让一部分用户以为"插件坏了"，所以文案必须解释原因（`FG-API-403` 的三层文案）。

## Alternatives

### 不管 Origin，靠"本机地址"隐含信任

很多本地工具就这么做（监听 `127.0.0.1` 就认为安全）。

- **否掉的原因**：浏览器里的任意网页都能向 `127.0.0.1:38080` 发请求（DNS rebinding / 简单 CORS 场景），本机监听**不等于**只有本机页面能调。安装/卸载这种副作用大的动作不能只靠"绑了 loopback"。

### 插件自建 token，页面通过 URL 参数或本地文件拿

- **否掉的原因**：token 要存哪里？存 `state.json` 则同机进程可读（挡不住本地进程）；存浏览器则要处理刷新与丢失。**威胁模型对不上** —— 我们要挡的是"跨站页面驱动浏览器"，Origin 校验正好对应；自研 token 挡不住真正的本地攻击者却增加一堆状态。

### 把子进程绑 `0.0.0.0` 以支持手机直连

- **否掉的原因**：MCP 端点无鉴权，等于把设备控制接口交给整个局域网。**默认必须是 `127.0.0.1`**；需要时由用户显式打开并看到警告。

### 给子进程加反向代理做鉴权

- **否掉的原因**：子进程的调用方是**桥**（本机进程），不是浏览器；中间加代理只会多一跳故障点。真要暴露到局域网，应该由用户自己的网络层（VPN / 反代）解决，而不是插件内建。

## 待确认

- `server.bind_address` 在三处出现：插件生成物、UX 端口页字段、子进程配置。MVP 的界面**是否暴露这个开关**（暴露则必须绑定警告文案）尚未最终拍板；当前文档按"可暴露 + 强制警告"写。
- `server.ws_port` 的归属未定（[`src/constants.ts`](../../src/constants.ts) 没有对应常量）。它与绑定地址同属"网络暴露面"，归属定下来后本文与端口页需要同步。
